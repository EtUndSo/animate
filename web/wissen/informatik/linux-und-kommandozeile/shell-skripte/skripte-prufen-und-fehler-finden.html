Worum es geht:

Ein Skript kann an seiner Schreibweise scheitern, an einem falschen Ablauf oder an einer Falle, die erst bei einem bestimmten Dateinamen zuschnappt. Dieser Abschnitt zeigt vier Werkzeuge dagegen: die Syntaxprüfung der bash, die Ablaufverfolgung, das Prüfprogramm ShellCheck und Probeläufe mit festen Testfällen.

Die Syntax prüfen: bash -n#

Ein vergessenes fi oder ein fehlendes Anführungszeichen fällt oft erst auf, wenn das Skript schon halb gelaufen ist. Man kann die bash ein Skript lesen lassen, ohne dass sie etwas ausführt.

Definition 10.1 (bash -n)

bash -n skript liest das Skript vollständig und prüft, ob es den Regeln der Shell-Sprache entspricht, führt aber keinen Befehl aus. Bei einem Syntaxfehler meldet es die Zeile, an der es den Fehler bemerkt hat, und endet mit dem Status 2; sonst mit 0.

kaputt.shBash
#!/bin/bash
# kaputt.sh: ein Skript mit einem Syntaxfehler
for datei in "$@"; do
    if [ -f "$datei" ]; then
        echo "$datei: eine Datei"
done
Konsole
$ bash -n kaputt.sh
kaputt.sh: line 6: syntax error near unexpected token `done'
kaputt.sh: line 6: `done'
$ echo $?
2
$ bash -n zaehle.sh
$ echo $?
0

Der Fehler ist das fehlende fi nach Zeile 5, gemeldet wird Zeile 6: Erst bei done merkt die bash, dass ein if noch offen ist, denn bis dahin hätte noch ein fi kommen können. Eine Fehlermeldung zeigt also, wo die Shell aufgeben musste, nicht unbedingt, wo der Fehler sitzt; die Ursache steht oft weiter oben. Abbildung 43 zeigt die Meldung im Terminal.

⁠Kurz gesagt: bash -n skript prüft die Schreibweise, ohne etwas auszuführen; die gemeldete Zeile ist die, an der die Shell aufgeben musste.

Den Ablauf verfolgen: bash -x#

Ist die Schreibweise in Ordnung, tut das Skript aber etwas anderes als gedacht, will man sehen, welche Befehle wirklich laufen und welche Werte die Variablen dabei haben.

Definition 10.2 (bash -x und set -x)

bash -x skript führt das Skript aus und schreibt vor jedem Befehl eine Zeile auf die Fehlerausgabe, die den Befehl nach der Expansion zeigt, mit einem + davor. set -x schaltet diese Ablaufverfolgung innerhalb eines Skripts oder der Befehlszeile ein, set +x wieder aus.

Konsole
$ bash -x bewertung.sh 80
+ punkte=80
+ ist_zahl 80
+ [[ 80 =~ ^[0-9]+$ ]]
+ ((  punkte > 100  ))
+ ((  punkte >= 90  ))
+ ((  punkte >= 75  ))
+ echo gut
gut

Man sieht den Weg durch die Verzweigung: Die Prüfungen auf 100 und 90 scheitern, die auf 75 trifft. In der Befehlszeile:

Konsole
$ set -x
$ echo "Hallo, $USER"
+ echo 'Hallo, student'
Hallo, student
$ set +x
+ set +x

Die Zeile nach dem + zeigt die Wörter so, wie das Programm sie bekommt: $USER ist eingesetzt, und einfache Anführungszeichen markieren, was ein einzelnes Argument ist. Damit sieht man genau die Wörter, um die es in Kapitel 5 ging. Das Zeichen + steht in der Variablen PS4; mit PS4='+ Zeile $LINENO: ' zeigt jede Zeile zusätzlich ihre Zeilennummer im Skript. Abbildung 44 ordnet die Spur dem Skript zu.

⁠Kurz gesagt: bash -x zeigt jeden ausgeführten Befehl mit den Wörtern, die er nach der Expansion bekommt.

Typische Fehler finden: ShellCheck#

Viele Fehler dieses Kapitels fallen erst bei bestimmten Daten auf, etwa bei einem Dateinamen mit Leerzeichen. Ein Skript kann hundertmal fehlerfrei laufen und beim nächsten Mal Unsinn machen. Lege zwei Textdateien an, eine mit Leerzeichen im Namen:

Konsole
$ mkdir texte
$ echo "Hallo Welt" > texte/gruss.txt
$ echo "Liebe Oma, danke für das Paket." > "texte/mein brief.txt"

Das folgende Skript soll die Wörter aller Textdateien eines Verzeichnisses zählen. Es enthält gleich mehrere Fehler:

fehlerhaft.shBash
#!/bin/bash
# fehlerhaft.sh: zählt die Wörter aller Textdateien in einem Verzeichnis
cd $1
for datei in $(ls *.txt); do
    woerter=$(wc -w < $datei)
    echo "$datei: $woerter Wörter"
    gesamt=$(( gesamt + woerter ))
done
echo "Zusammen: $gesamt Wörter in $verzeichnis"
Konsole
$ bash fehlerhaft.sh texte
gruss.txt: 2 Wörter
fehlerhaft.sh: line 5: mein: No such file or directory
mein:  Wörter
fehlerhaft.sh: line 5: brief.txt: No such file or directory
brief.txt:  Wörter
Zusammen: 2 Wörter in
Definition 10.3 (ShellCheck)

ShellCheck ist ein Programm, das ein Shell-Skript liest, ohne es auszuführen, und es mit einer Sammlung bekannter Fehlermuster vergleicht. Jede Meldung zeigt die Stelle, eine Nummer der Form SC2086, eine Einstufung (error, warning, info oder style) und einen kurzen Text; zu jeder Nummer gibt es eine Seite mit Erklärung und Abhilfe. Findet es etwas, endet es mit dem Status 1.

Ein Programm, das Quelltext untersucht, ohne ihn laufen zu lassen, nennt man ein Werkzeug zur statischen Analyse. Welche Shell-Sprache gemeint ist, liest ShellCheck aus der Shebang-Zeile.

Konsole
$ shellcheck fehlerhaft.sh

Jede Meldung entspricht einer Regel dieses Kapitels: cd ohne Prüfung (Abschnitt 8.3), Variablen ohne Anführungszeichen (Abschnitt 3.5), eine Schleife über die Ausgabe von ls (Abschnitt 5.2), ein Muster, dessen Treffer mit einem Strich beginnen und dann als Option gelten könnten, und eine Variable, die nie belegt wird, hier ein vergessenes verzeichnis=$1. Auch die Pipe-Falle kennt ShellCheck: Für die fehlerhafte minuten.sh aus Abschnitt 6.4 meldet es, dass summe nur im Kindprozess der Pipeline verändert wird (SC2030 und SC2031). Die verbesserte Fassung:

woerter.shBash
#!/bin/bash
# woerter.sh: zählt die Wörter aller Textdateien in einem Verzeichnis
verzeichnis=$1
cd "$verzeichnis" || exit 1
gesamt=0
for datei in ./*.txt; do
    [ -f "$datei" ] || continue
    woerter=$(wc -w < "$datei")
    echo "$datei: $woerter Wörter"
    gesamt=$(( gesamt + woerter ))
done
echo "Zusammen: $gesamt Wörter in $verzeichnis"
Konsole
$ shellcheck woerter.sh
$ echo $?
0
$ bash woerter.sh texte
./gruss.txt: 2 Wörter
./mein brief.txt: 6 Wörter
Zusammen: 8 Wörter in texte

[ -f "$datei" ] | continue| fängt den Fall ab, dass das Muster nichts findet und als Text stehen bleibt. ShellCheck ist auf dem Testsystem schon installiert; sonst installiert man es mit sudo apt install shellcheck (Kapitel 9, Abschnitt 6.3), und unter https://www.shellcheck.net gibt es dieselbe Prüfung im Browser. Abbildung 45 hebt die Meldungen hervor.

HintergrundWenn ShellCheck sich irrt

ShellCheck kennt die Absicht nicht. In alle.sh aus Abschnitt 2.4 steht $* absichtlich ohne Anführungszeichen, um den Fehler vorzuführen, und ShellCheck meldet ihn trotzdem. Will man eine Meldung an einer Stelle bewusst hinnehmen, schreibt man direkt darüber einen Kommentar der Form # shellcheck disable=SC2048; ShellCheck schweigt dann für den folgenden Befehl. Mit shellcheck -S warning skript zeigt es nur Meldungen ab der Einstufung warning. Eine Meldung abzuschalten, statt den Fehler zu verstehen, ist allerdings selten die richtige Wahl.

⁠Kurz gesagt: shellcheck skript findet typische Fehler wie fehlende Anführungszeichen, ungeprüftes cd und Schleifen über ls, bevor sie bei bestimmten Daten zuschlagen.

Der Probelauf mit echo#

Ein Skript, das löscht, verschiebt oder überschreibt, testet man ungern echt. Man möchte erst sehen, welche Befehle es ausführen würde.

Definition 10.4 (Probelauf)

Ein Probelauf ist ein Lauf, in dem vor jedem verändernden Befehl echo steht. Das Skript gibt den Befehl dann mit allen eingesetzten Wörtern aus, statt ihn auszuführen.

In loesche.sh wird dafür nur eine Zeile geändert; ein Kommentar markiert sie, damit man sie nach dem Test wiederfindet:

loesche.shBash
#!/bin/bash
# loesche.sh: Probelauf, zeigt den Löschbefehl nur an
if ! cd "$1"; then
    echo "loesche.sh: kann nicht nach '$1' wechseln, lösche nichts" >&2
    exit 1
fi
echo rm -f -- *.tmp    # PROBELAUF: echo vor rm
echo "Aufgeräumt in $PWD"
Konsole
$ touch alt/c.tmp alt/d.tmp
$ ./loesche.sh alt
rm -f -- c.tmp d.tmp
Aufgeräumt in /home/student/linuxk10/alt
$ ls alt
c.tmp  d.tmp

Die Ausgabe zeigt den fertigen Befehl, nachdem die Pfadnamen-Erweiterung *.tmp ersetzt hat; die Dateien sind noch da. Danach entfernt man das echo wieder. Abbildung 46 vergleicht beide Läufe.

⁠Kurz gesagt: Ein echo vor einem gefährlichen Befehl zeigt ihn mit allen eingesetzten Wörtern, ohne ihn auszuführen.

Testfälle#

Probieren von Hand prüft meist nur die Fälle, an die man ohnehin gedacht hat. Systematisch wird es, wenn man vorher aufschreibt, was bei welcher Eingabe herauskommen muss, und das automatisch vergleicht.

Definition 10.5 (Testfall)

Ein Testfall ist eine Eingabe zusammen mit dem Ergebnis, das ein Programm bei dieser Eingabe liefern muss. Gute Testfälle decken gewöhnliche Eingaben ab, die Grenzen zwischen zwei Ergebnissen und ungültige Eingaben.

Für bewertung.sh liegen die Grenzen bei 90, 75 und 50: 90 muss „sehr gut“ sein, 89 schon „gut“, und genauso gehört an die beiden anderen Grenzen je ein Wert darauf und einer knapp darunter. Ungültig sind etwa 101, abc und eine leere Eingabe; dort soll das Skript nichts auf die Standardausgabe schreiben. Ein kleines Testskript ruft das zu prüfende Skript mit jedem Fall auf und vergleicht; mit einem Argument prüft es ein anderes Skript als ./bewertung.sh:

teste_bewertung.shBash
#!/bin/bash
# teste_bewertung.sh: prüft bewertung.sh mit festen Testfällen
#   Aufruf: teste_bewertung.sh [SKRIPT]   (ohne Argument: ./bewertung.sh)
skript=./bewertung.sh
if [ $# -gt 0 ]; then
    skript=$1
fi
fehler=0

pruefe() {
    local erwartet=$1 eingabe=$2 ergebnis
    ergebnis=$("$skript" "$eingabe" 2> /dev/null)
    if [ "$ergebnis" = "$erwartet" ]; then
        echo "ok      $eingabe -> $ergebnis"
    else
        echo "FEHLER  $eingabe -> '$ergebnis', erwartet '$erwartet'"
        fehler=$(( fehler + 1 ))
    fi
}

pruefe "sehr gut" 100
pruefe "sehr gut" 90
pruefe "gut" 89
pruefe "gut" 75
pruefe "bestanden" 74
pruefe "bestanden" 50
pruefe "nicht bestanden" 49
pruefe "nicht bestanden" 0
pruefe "" 101
pruefe "" abc
pruefe "" ""
echo "$fehler Fehler"
[ "$fehler" -eq 0 ]

Die letzte Zeile macht aus dem Ergebnis den Exit-Status des Testskripts. Mit der alten Fassung aus Abschnitt 4.3, die Abschnitt 7.4 als bewertung_alt.sh aufgehoben hat, und mit der neuen:

Nach jeder Änderung an bewertung.sh genügt ein Aufruf des Testskripts, um zu sehen, ob noch alles stimmt. Abbildung 47 zeigt die Tabelle der Fälle.

HintergrundEine Lücke, die auch diese Testfälle übersehen

Auch die neue Fassung hat noch eine Lücke, und keiner der elf Fälle trifft sie: Zahlen mit einer führenden Null. ist_zahl lässt 0100 durch, denn es besteht nur aus Ziffern. Die Arithmetik der bash liest eine Zahl, die mit 0 beginnt, aber in der Oktalschreibweise (Kapitel 7, Abschnitt 3.3), und dort ist 0100 gleich 64:

Konsole
$ echo $(( 0100 ))
64
$ ./bewertung.sh 0100
bestanden
$ ./bewertung.sh 08 2> /dev/null
nicht bestanden

Bei 08 meldet die bash zusätzlich viermal den Fehler value too great for base auf der Fehlerausgabe, denn 8 ist keine Ziffer der Oktalschreibweise; das Skript endet trotzdem mit „nicht bestanden“ und dem Status 0. Abhilfe schafft ein strengerer Ausdruck in ist_zahl, ^(0|[1-9][0-9]*)$, der eine führende Null nur für die Zahl 0 selbst erlaubt (Kapitel 6, Abschnitt 7.4). Oder man schreibt in der Arithmetik 10#$punkte; die Vorsilbe 10# liest die Ziffern ausdrücklich im Dezimalsystem. Ob 0100 abgelehnt oder als 100 gelesen werden soll, muss man vorher festlegen, und genau dazu zwingt ein weiterer Testfall wie pruefe "" 0100.

⁠Kurz gesagt: Testfälle halten vorher fest, was bei gewöhnlichen, grenznahen und ungültigen Eingaben herauskommen muss; ein Testskript vergleicht das nach jeder Änderung.

Aufräumen#

Alle Übungen dieses Kapitels liefen im Übungsverzeichnis. Wenn du die Aufgaben erledigt hast, entfernst du es samt Inhalt; cd ohne Argument wechselt vorher ins Heimatverzeichnis, damit du nicht im zu löschenden Verzeichnis stehst:

Konsole
$ cd
$ rm -r ~/linuxk10

Skripte, die du behalten willst, kopierst du vorher nach ~/.local/bin (Abschnitt 1.8). Die Änderung an PATH aus diesem Kapitel galt nur für die damalige Shell und ist mit ihr verschwunden.

Aufgabe 37 ★★★ Testfälle für zaehle.sh

Schreibe ein Testskript teste_zaehle.sh, das die fertige zaehle.sh mit vier Fällen aufruft und jeweils nur den Exit-Status mit dem erwarteten vergleicht: keine Argumente (2), eine vorhandene Datei (0), eine fehlende Datei (1), eine vorhandene und eine fehlende (1). Die Ausgaben von zaehle.sh sollen dabei nicht erscheinen.

Lösung

Die Funktion erwarte bekommt den erwarteten Status und danach die Argumente für zaehle.sh. shift entfernt den erwarteten Status, so dass "$@" nur noch die Argumente enthält. Beide Ausgaben von zaehle.sh gehen nach /dev/null, und $? wird sofort in ist gesichert:

teste_zaehle.shBash
#!/bin/bash
# teste_zaehle.sh: prüft die Exit-Status von zaehle.sh
fehler=0

erwarte() {
    local soll=$1 ist
    shift
    ./zaehle.sh "$@" > /dev/null 2>&1
    ist=$?
    if [ "$ist" -eq "$soll" ]; then
        echo "ok      zaehle.sh $* -> $ist"
    else
        echo "FEHLER  zaehle.sh $* -> $ist, erwartet $soll"
        fehler=$(( fehler + 1 ))
    fi
}

erwarte 2
erwarte 0 einkauf.txt
erwarte 1 gibtsnicht.txt
erwarte 1 einkauf.txt gibtsnicht.txt
echo "$fehler Fehler"
[ "$fehler" -eq 0 ]
Konsole
$ chmod +x teste_zaehle.sh
$ ./teste_zaehle.sh
ok      zaehle.sh  -> 2
ok      zaehle.sh einkauf.txt -> 0
ok      zaehle.sh gibtsnicht.txt -> 1
ok      zaehle.sh einkauf.txt gibtsnicht.txt -> 1
0 Fehler
$ echo $?
0

In der Meldung steht $*, denn dort sollen die Argumente bewusst zu einem Text verbunden werden (Abschnitt 2.5). Hier passt auch die Vorlage aus teste_bewertung.sh nicht ganz, denn dort wurde die Ausgabe verglichen, hier der Status; beide Testskripte enden selbst mit 0 nur dann, wenn kein Fall gescheitert ist.

Definition 10.2 (bash -x und set -x)

bash -x skript führt das Skript aus und schreibt vor jedem Befehl eine Zeile auf die Fehlerausgabe, die den Befehl nach der Expansion zeigt, mit einem + davor. set -x schaltet diese Ablaufverfolgung innerhalb eines Skripts oder der Befehlszeile ein, set +x wieder aus.

$ bash -x bewertung.sh 80
↗
$ set -x
$ echo "Hallo, $USER"
$ set +x
↗
Typische Fehler finden: ShellCheck
$ mkdir texte
$ echo "Hallo Welt" > texte/gruss.txt
$ echo "Liebe Oma, danke für das Paket." > "texte/mein brief.txt"
↗
$ bash fehlerhaft.sh texte
↗
Definition 10.3 (ShellCheck)

ShellCheck ist ein Programm, das ein Shell-Skript liest, ohne es auszuführen, und es mit einer Sammlung bekannter Fehlermuster vergleicht. Jede Meldung zeigt die Stelle, eine Nummer der Form SC2086, eine Einstufung (error, warning, info oder style) und einen kurzen Text; zu jeder Nummer gibt es eine Seite mit Erklärung und Abhilfe. Findet es etwas, endet es mit dem Status 1.

$ shellcheck fehlerhaft.sh
↗
$ shellcheck woerter.sh
$ bash woerter.sh texte
↗
Der Probelauf mit echo
Definition 10.4 (Probelauf)

Ein Probelauf ist ein Lauf, in dem vor jedem verändernden Befehl echo steht. Das Skript gibt den Befehl dann mit allen eingesetzten Wörtern aus, statt ihn auszuführen.

$ touch alt/c.tmp alt/d.tmp
$ ./loesche.sh alt
$ ls alt
↗
Testfälle
Definition 10.5 (Testfall)

Ein Testfall ist eine Eingabe zusammen mit dem Ergebnis, das ein Programm bei dieser Eingabe liefern muss. Gute Testfälle decken gewöhnliche Eingaben ab, die Grenzen zwischen zwei Ergebnissen und ungültige Eingaben.

$ chmod +x teste_bewertung.sh
$ ./teste_bewertung.sh ./bewertung_alt.sh
$ ./teste_bewertung.sh

Zusammenfassung

Begriffe
  • bash -n skript – bash -n skript liest das Skript vollständig und prüft, ob es den Regeln der Shell-Sprache entspricht, führt aber keinen Befehl aus.
  • bash -x skript – bash -x skript führt das Skript aus und schreibt vor jedem Befehl eine Zeile auf die Fehlerausgabe, die den Befehl nach der Expansion zeigt, mit einem + davor.
  • ShellCheck – ShellCheck ist ein Programm, das ein Shell-Skript liest, ohne es auszuführen, und es mit einer Sammlung bekannter Fehlermuster vergleicht.
  • Probelauf – Ein Probelauf ist ein Lauf, in dem vor jedem verändernden Befehl echo steht.
  • Testfall – Ein Testfall ist eine Eingabe zusammen mit dem Ergebnis, das ein Programm bei dieser Eingabe liefern muss.
Zusammenhänge
  • Zu „Die Syntax prüfen: bash -n“: bash -n skript prüft die Schreibweise, ohne etwas auszuführen; die gemeldete Zeile ist die, an der die Shell aufgeben musste.
  • Zu „Den Ablauf verfolgen: bash -x“: bash -x zeigt jeden ausgeführten Befehl mit den Wörtern, die er nach der Expansion bekommt.
  • Zu „Typische Fehler finden: ShellCheck“: shellcheck skript findet typische Fehler wie fehlende Anführungszeichen, ungeprüftes cd und Schleifen über ls, bevor sie bei bestimmten Daten zuschlagen.
  • Zu „Der Probelauf mit echo“: Ein echo vor einem gefährlichen Befehl zeigt ihn mit allen eingesetzten Wörtern, ohne ihn auszuführen.
  • Zu „Testfälle“: Testfälle halten vorher fest, was bei gewöhnlichen, grenznahen und ungültigen Eingaben herauskommen muss; ein Testskript vergleicht das nach jeder Änderung.
