Worum es geht:

Viele Prozesse im Baum aus Unterabschnitt 1.7 hat niemand von Hand gestartet, und sie haben kein Terminal. Dieser Abschnitt erklärt solche Dienste, das Programm systemd, das sie startet und überwacht, und wie man sie mit systemctl ansieht und steuert. Zum Üben legst du einen eigenen kleinen Dienst an.

Der Dienst#

Manche Arbeiten soll ein Rechner erledigen, ohne dass jemand angemeldet ist: zu festen Zeiten Aufgaben starten, die Uhr stellen, Meldungen sammeln, Anfragen aus dem Netz beantworten. Programme dafür laufen dauerhaft im Hintergrund.

Definition 7.1 (Dienst, Daemon)

Ein Dienst (englisch „service“, unter Unix auch „daemon“) ist ein Programm, das im Hintergrund dauerhaft läuft und anderen Programmen oder dem System eine Leistung anbietet. Ein Dienst hat kein steuerndes Terminal, wird nicht von einer Shell gestartet und läuft oft unter einem eigenen Benutzer.

Ein paar Dienste des Testsystems, mit Benutzer, PPID und Terminal:

Konsole
$ ps -o user:16,pid,ppid,tty,comm -C cron,chronyd,systemd-resolve,rsyslogd,dbus-daemon
USER                 PID    PPID TT       COMMAND
systemd-resolve       83       1 ?        systemd-resolve
root                 160       1 ?        cron
messagebus           161       1 ?        dbus-daemon
syslog               186       1 ?        rsyslogd
_chrony              232     159 ?        chronyd
_chrony              235     232 ?        chronyd

user:16 macht die Spalte 16 Zeichen breit, damit lange Namen nicht abgeschnitten werden. Kein Dienst hat ein Terminal (?), die meisten sind Kinder von systemd, und viele gehören nicht root. cron startet Aufgaben zu festen Zeiten, chronyd stellt die Uhr, rsyslogd schreibt Meldungen in Dateien unter /var/log, systemd-resolved übersetzt Rechnernamen in Adressen, und dbus-daemon vermittelt Nachrichten zwischen Programmen. Abbildung 25 vergleicht einen Dienst mit einem Programm, das du im Terminal startest.

⁠Kurz gesagt: Ein Dienst ist ein Programm ohne Terminal, das dauerhaft im Hintergrund für das System arbeitet, oft unter eigenem Benutzer.

systemd: der Prozess mit der Nummer 1#

Jemand muss die Dienste beim Hochfahren starten, in der richtigen Reihenfolge, sie neu starten, wenn sie abstürzen, und beim Herunterfahren beenden. Unter Ubuntu erledigt das der Prozess, der ohnehin an der Wurzel des Baums steht.

Definition 7.2 (systemd als Dienstverwalter)

systemd ist als Prozess 1 der Dienstverwalter des Systems: Er startet beim Hochfahren die Dienste, überwacht sie, startet sie bei Bedarf neu und beendet sie beim Herunterfahren. Für jeden angemeldeten Benutzer läuft zusätzlich eine eigene Instanz systemd --user, die die Dienste dieses Benutzers verwaltet. Gesteuert wird systemd mit dem Befehl systemctl.

Konsole
$ ps -o pid,ppid,user,cmd -C systemd
    PID    PPID USER     CMD
      1       0 root     /sbin/init
    383       1 student  /usr/lib/systemd/systemd --user
$ ls -l /sbin/init
lrwxrwxrwx 1 root root 22 Jul 27 22:44 /sbin/init -> ../lib/systemd/systemd
$ systemctl is-system-running
running

/sbin/init ist nur ein symbolischer Link auf systemd. Die Instanz des Benutzers student hat die Nummer 383 und ist ein Kind des Prozesses 1. systemctl is-system-running meldet, dass der Start abgeschlossen ist und alles läuft. Die Benutzerinstanz beginnt mit der ersten Anmeldung des Benutzers und endet mit seiner letzten Sitzung, samt den Diensten, die sie verwaltet. Nur wenn der Verwalter für den Benutzer das Weiterlaufen ohne Anmeldung eingeschaltet hat (englisch „linger“), bleibt sie bestehen.

Unter WSL läuft systemd nur, wenn es in der Datei /etc/wsl.conf unter [boot] mit der Zeile systemd=true eingeschaltet ist. Bei einer Installation wie in Kapitel 1, Abschnitt 4.2 bringt Ubuntu diese Zeile selbst mit; auf dem Testsystem ist sie gesetzt. Meldet systemctl bei dir „System has not been booted with systemd as init system (PID 1)“, fehlt sie: Trag sie mit sudo nano /etc/wsl.conf ein und starte WSL neu, indem du in PowerShell wsl --shutdown eingibst und das Terminal wieder öffnest.

⁠Kurz gesagt: systemd startet, überwacht und beendet als Prozess 1 die Dienste des Systems, eine eigene Instanz die jedes Benutzers; gesteuert wird es mit systemctl.

Die Unit#

systemd verwaltet nicht nur Dienste, sondern auch Zeitpläne, eingehängte Dateisysteme und Gruppen von Diensten. Für all das braucht es einen gemeinsamen Begriff.

Definition 7.3 (Unit)

Eine Unit ist ein Ding, das systemd verwaltet. Ihr Name endet mit ihrer Art, etwa .service für einen Dienst, .timer für einen Zeitplan, .mount für ein eingehängtes Dateisystem oder .target für eine Gruppe von Units, die zusammen einen Zustand des Systems bilden.

systemctl list-units zeigt die Units, die systemd gerade geladen hat; --type und --state schränken die Liste ein:

Konsole
$ systemctl list-units --type=service --state=running
  UNIT                    LOAD   ACTIVE SUB     DESCRIPTION
  chrony.service          loaded active running chrony, an NTP client/s…
  console-getty.service   loaded active running Console Getty
  cron.service            loaded active running Regular background prog…
  dbus.service            loaded active running D-Bus System Message Bus
  getty@tty1.service      loaded active running Getty on tty1
  networkd-dispatcher.se… loaded active running Dispatcher daemon for s…
  rsyslog.service         loaded active running System Logging Service
  systemd-journald.servi… loaded active running Journal Service
  systemd-logind.service  loaded active running User Login Management
  systemd-resolved.servi… loaded active running Network Name Resolution
  systemd-udevd.service   loaded active running Rule-based Manager for …
  unattended-upgrades.se… loaded active running Unattended Upgrades Shu…
  user@1000.service       loaded active running User Manager for UID 10…
  wsl-pro.service         loaded active running Bridge to Ubuntu Pro ag…

Legend: LOAD   → Reflects whether the unit definition was properly loaded.
        ACTIVE → The high-level unit activation state, i.e. generalization of SUB.
        SUB    → The low-level unit activation state, values depend on unit type.

14 loaded units listed.

LOAD sagt, ob systemd die Beschreibung der Unit lesen konnte, ACTIVE den groben Zustand (active, inactive, failed), SUB den genauen (running für einen laufenden Dienst); zu lange Namen kürzt systemctl mit „…“ auf die Breite des Terminals. user@1000.service ist die Benutzerinstanz von student, wsl-pro.service ein Dienst, den es nur unter WSL gibt. Passt eine Ausgabe von systemctl nicht auf den Bildschirm, zeigt es sie im Seitenanzeiger less (Kapitel 2, Abschnitt 4.4); q beendet ihn, und mit --no-pager schreibt systemctl direkt ins Terminal.

⁠Kurz gesagt: Eine Unit ist alles, was systemd verwaltet, ein Dienst ist eine Unit mit der Endung .service; systemctl list-units zeigt sie.

Den Zustand ansehen: systemctl status#

Für einen einzelnen Dienst will man meist auf einen Blick wissen: Läuft er, seit wann, unter welcher PID, und startet er beim Hochfahren?

Definition 7.4 (systemctl status, is-active, is-enabled)

systemctl status unit zeigt für eine Unit, woher ihre Beschreibung stammt und ob sie beim Start mitgestartet wird (Loaded), ihren Zustand seit wann (Active), die PID ihres Hauptprozesses (Main PID), ihren Verbrauch, ihre Prozesse (CGroup) und ihre letzten Meldungen. systemctl is-active unit und systemctl is-enabled unit antworten nur mit einem Wort.

Ansehen darf jeder Benutzer, auch die Dienste des Systems:

Konsole
$ systemctl status cron
● cron.service - Regular background program processing daemon
     Loaded: loaded (/usr/lib/systemd/system/cron.service; enabled; preset: enabled)
     Active: active (running) since Tue 2026-11-10 15:24:41 CET; 4min 23s ago
 Invocation: 5bebfba81d7240c09d04b95ea11dc2b4
       Docs: man:cron(8)
   Main PID: 160 (cron)
      Tasks: 1 (limit: 38204)
     Memory: 508K (peak: 2M)
        CPU: 15ms
     CGroup: /system.slice/cron.service
             └─160 /usr/sbin/cron -f -P
Konsole
$ systemctl is-active cron
active
$ systemctl is-enabled cron
enabled

Die erste Zeile nennt den Namen und die Beschreibung der Unit. Der Punkt davor fasst den Zustand zusammen, im Terminal auch mit einer Farbe: $\bullet$ (grün) für „aktiv“, $\circ$ für „inaktiv“ und $\times$ (rot) für „fehlgeschlagen“. Loaded nennt die Datei mit der Beschreibung und enabled: cron startet beim Hochfahren. Active sagt, dass der Dienst seit gut vier Minuten läuft, also seit dem letzten Start von WSL. Main PID ist die 160 aus Unterabschnitt 2.4. CGroup ist die Gruppe von Prozessen, in die systemd jeden Dienst steckt; so findet es auch alle Kinder eines Dienstes wieder. Die letzten Meldungen des Dienstes, die status sonst darunter zeigt, fehlen hier, weil student sie auf dem Testsystem nicht lesen darf; manchmal steht dort stattdessen die Warnung some journal files were not opened due to insufficient permissions. Bei dir stehen sie vielleicht da: Der erste Benutzer einer gewöhnlichen Ubuntu-Installation, am Desktop wie unter WSL, darf sie meist lesen. Abbildung 26 zeigt die Ausgabe so, wie sie in einem kleinen Terminalfenster erscheint, und geht ihre Teile der Reihe nach durch.

⁠Kurz gesagt: systemctl status zeigt Zustand, Hauptprozess und letzte Meldungen einer Unit; is-active und is-enabled antworten mit einem Wort.

Die Unit-Datei#

Woher weiß systemd, welches Programm zu cron.service gehört, und dass es beim Hochfahren starten soll? Das steht in einer Textdatei.

Definition 7.5 (Unit-Datei)

Eine Unit-Datei beschreibt eine Unit in Abschnitten, deren Name in eckigen Klammern steht, und Zeilen der Form Name=Wert. [Unit] enthält allgemeine Angaben wie Description= und die Reihenfolge zu anderen Units (After=), [Service] bei einem Dienst das Programm (ExecStart=) und wie es zu betreuen ist, und [Install], wann die Unit beim Start mitgestartet wird (WantedBy=). Die Unit-Dateien des Systems liegen unter /usr/lib/systemd/system, eigene Änderungen des Verwalters unter /etc/systemd/system.

systemctl cat unit zeigt die Datei einer Unit:

Konsole
$ systemctl cat cron
# /usr/lib/systemd/system/cron.service
[Unit]
Description=Regular background program processing daemon
Documentation=man:cron(8)
After=remote-fs.target nss-user-lookup.target

[Service]
EnvironmentFile=-/etc/default/cron
ExecStart=/usr/sbin/cron -f -P $EXTRA_OPTS
IgnoreSIGPIPE=false
KillMode=process
Restart=on-failure
SyslogFacility=cron

[Install]
WantedBy=multi-user.target

Die erste Zeile nennt den Ort der Datei. ExecStart= ist das Programm samt Argumenten; -f sagt cron, dass es im Vordergrund bleiben soll, statt sich selbst vom Terminal zu lösen, denn darum kümmert sich systemd. Restart=on-failure lässt systemd den Dienst neu starten, wenn er unerwartet endet. WantedBy=multi-user.target bedeutet: Der Dienst gehört zum gewöhnlichen Betrieb des Systems und startet mit ihm. Abbildung 27 ordnet die Zeilen.

⁠Kurz gesagt: Eine Unit-Datei beschreibt eine Unit in den Abschnitten [Unit], [Service] und [Install]; systemctl cat zeigt sie.

Ein eigener Dienst: starten und stoppen#

Dienste des Systems startet und stoppt nur root, und ein Fehler dabei kann das System stören. Zum Üben eignet sich deshalb ein eigener Dienst, den deine Benutzerinstanz von systemd verwaltet. Er braucht kein sudo und berührt nichts außerhalb deines Heimatverzeichnisses.

Definition 7.6 (Benutzerdienst, start, stop)

Ein Benutzerdienst ist ein Dienst, den die Instanz systemd --user eines Benutzers verwaltet; er läuft mit den Rechten dieses Benutzers. Seine Unit-Datei liegt unter ~/.config/systemd/user, und systemctl --user richtet jeden Befehl an diese Instanz. Nach dem Anlegen oder Ändern einer Unit-Datei liest systemctl --user daemon-reload die Dateien neu ein. systemctl start unit startet eine Unit, systemctl stop unit beendet sie.

Achtung: Nur der eigene Übungsdienst

Starte, stoppe oder ändere in diesem Kapitel nur den eigenen Benutzerdienst k8eieruhr. Dienste des Systems siehst du nur an; sudo systemctl stop an einem fremden Dienst kann das Netz, die Anmeldung oder die Protokolle lahmlegen. Der Übungsdienst selbst wartet nur; er lässt sich jederzeit mit systemctl --user stop k8eieruhr beenden und durch Löschen seiner Datei entfernen.

Der Übungsdienst ist eine Eieruhr: Er wartet zehn Minuten. Die Unit-Datei schreibst du mit einem Here-Document (Kapitel 4, Abschnitt 3.2):

Konsole
$ mkdir -p ~/.config/systemd/user
$ cat > ~/.config/systemd/user/k8eieruhr.service <<ENDE
> [Unit]
> Description=Eieruhr zum Üben
>
> [Service]
> ExecStart=/usr/bin/sleep 600
> Restart=on-failure
>
> [Install]
> WantedBy=default.target
> ENDE
$ systemctl --user daemon-reload
$ systemctl --user status k8eieruhr
○ k8eieruhr.service - Eieruhr zum Üben
     Loaded: loaded (/home/student/.config/systemd/user/k8eieruhr.service; disabled; preset: enabled)
     Active: inactive (dead)

default.target ist bei einem Benutzerdienst der Zustand „Benutzer angemeldet“. Den Teil .service darf man bei systemctl weglassen. systemd kennt die Unit jetzt, sie ist aber nicht aktiv (inactive) und startet nicht von selbst (disabled).

Konsole
$ systemctl --user start k8eieruhr
$ systemctl --user status k8eieruhr
● k8eieruhr.service - Eieruhr zum Üben
     Loaded: loaded (/home/student/.config/systemd/user/k8eieruhr.service; disabled; preset: enabled)
     Active: active (running) since Tue 2026-11-10 15:29:07 CET; 418ms ago
 Invocation: 1e38067901944c18bc32b96d106e8f58
   Main PID: 820 (sleep)
      Tasks: 1 (limit: 38204)
     Memory: 1.3M (peak: 1.7M)
        CPU: 13ms
     CGroup: /user.slice/user-1000.slice/user@1000.service/app.slice/k8eieruhr.service
             └─820 /usr/bin/sleep 600
...

Der Dienst läuft, sein Hauptprozess ist ein sleep 600 mit der PID 820, und dessen Elternprozess ist die Benutzerinstanz von systemd, nicht deine Shell. Unter der Zeile CGroup zeigt status noch die letzten Meldungen des Dienstes, hier die über seinen Start; sie sind im Kapitel weggelassen.

Konsole
$ systemctl --user is-active k8eieruhr
active
Konsole
$ systemctl --user stop k8eieruhr
$ systemctl --user is-active k8eieruhr
inactive

stop schickt den Prozessen des Dienstes SIGTERM und wartet, bis sie enden; wer nach einer Frist noch läuft, bekommt SIGKILL. systemctl restart stoppt und startet in einem Schritt. Für die Dienste des Systems lauten die Befehle genauso, nur ohne --user und mit sudo davor.

⁠Kurz gesagt: Ein Benutzerdienst wird mit einer Unit-Datei unter ~/.config/systemd/user angelegt und mit systemctl --user start und stop gesteuert; nach jeder Änderung der Datei folgt daemon-reload.

systemd wacht: Neustart nach einem Absturz#

Ein Dienst, der abstürzt, soll nicht stundenlang ausfallen, bis es jemand bemerkt. Weil systemd der Elternprozess jedes Dienstes ist, erfährt es sofort, wenn einer endet, und kann darauf reagieren.

Definition 7.7 (Restart=)

Die Zeile Restart= im Abschnitt [Service] legt fest, wann systemd einen beendeten Dienst neu startet: no nie (Standard), on-failure nur nach einem Fehler, always immer. Als Fehler gilt ein Exit-Status ungleich 0 und ein Ende durch ein Signal, außer durch SIGHUP, SIGINT, SIGTERM und SIGPIPE. Nach systemctl stop startet systemd nie neu. Wie lange es vor einem Neustart wartet, legt RestartSec= fest; ohne die Zeile sind es 100 Millisekunden.

systemctl show -p MainPID nennt nur die PID des Hauptprozesses, und journalctl --user -u k8eieruhr -n 4 zeigt die letzten vier Meldungen, die über die Eieruhr gesammelt wurden. Die Eieruhr hat Restart=on-failure:

Konsole
$ systemctl --user start k8eieruhr
$ systemctl --user show -p MainPID k8eieruhr
MainPID=829
$ kill -9 829
$ systemctl --user show -p MainPID k8eieruhr
MainPID=833
$ journalctl --user -u k8eieruhr -n 4
Nov 10 15:29:10 labor systemd[383]: k8eieruhr.service: Main process exited, code=killed, status=9/KILL
Nov 10 15:29:10 labor systemd[383]: k8eieruhr.service: Failed with result 'signal'.
Nov 10 15:29:11 labor systemd[383]: k8eieruhr.service: Scheduled restart job, restart counter is at 1.
Nov 10 15:29:11 labor systemd[383]: Started k8eieruhr.service - Eieruhr zum Üben.
$ kill 833
$ systemctl --user is-active k8eieruhr
inactive

Nach SIGKILL läuft der Dienst kurz darauf wieder, mit dem neuen Hauptprozess 833. journalctl zeigt die Meldungen von systemd dazu: Der Hauptprozess wurde durch SIGKILL beendet, das gilt als Fehler, ein Neustart ist geplant und ausgeführt. Nach SIGTERM dagegen bleibt der Dienst aus, denn ein Ende durch SIGTERM gilt als gewolltes Ende. Abbildung 28 zeigt den Ablauf.

⁠Kurz gesagt: Mit Restart=on-failure startet systemd einen Dienst neu, der mit einem Fehler oder durch ein Signal wie SIGKILL endet, nicht aber nach SIGTERM oder stop.

Beim Start mitstarten: enable#

start startet einen Dienst jetzt. Ob er auch nach dem nächsten Hochfahren läuft, ist eine getrennte Frage, und dafür gibt es einen eigenen Befehl.

Definition 7.8 (enable, disable)

systemctl enable unit legt fest, dass die Unit künftig mitgestartet wird, wenn das Ziel aus ihrer Zeile WantedBy= erreicht wird. Dazu legt es einen symbolischen Link im Verzeichnis <ziel>.wants an; es startet die Unit nicht. systemctl disable unit entfernt den Link wieder. Wer beides auf einmal will, schreibt enable --now.

Konsole
$ systemctl --user enable k8eieruhr
Created symlink '/home/student/.config/systemd/user/default.target.wants/k8eieruhr.service' → '/home/student/.config/systemd/user/k8eieruhr.service'.
$ systemctl --user is-enabled k8eieruhr
enabled
$ ls -l ~/.config/systemd/user/default.target.wants
total 0
lrwxrwxrwx 1 student student 52 Nov 10 15:29 k8eieruhr.service -> /home/student/.config/systemd/user/k8eieruhr.service
$ systemctl --user is-active k8eieruhr
inactive
$ systemctl --user disable k8eieruhr
Removed '/home/student/.config/systemd/user/default.target.wants/k8eieruhr.service'.
$ systemctl --user is-enabled k8eieruhr
disabled

Nach enable steht im Verzeichnis default.target.wants ein symbolischer Link auf die Unit-Datei (Kapitel 3, Abschnitt 8.5); trotzdem läuft die Eieruhr nicht, denn enable startet nichts. Beim nächsten Erreichen von default.target, also bei der nächsten Anmeldung, würde systemd den Link finden und die Eieruhr starten. disable entfernt den Link. Abbildung 29 stellt start und enable gegenüber.

⁠Kurz gesagt: enable sorgt über einen symbolischen Link dafür, dass eine Unit beim nächsten Start mitstartet, start startet sie jetzt; beides ist unabhängig voneinander.

Dienste unter eigenen Benutzern#

Unterabschnitt 7.1 hat gezeigt, dass viele Dienste nicht root gehören. Das ist kein Zufall, sondern steht in ihrer Unit-Datei.

Definition 7.9 (User=)

Die Zeile User= im Abschnitt [Service] nennt den Benutzer, unter dem systemd das Programm des Dienstes startet. Fehlt sie, läuft ein Dienst des Systems als root. Bei einem Benutzerdienst ist die Zeile überflüssig, denn er läuft immer unter dem Benutzer seiner Instanz.

Konsole
$ grep -E '^(User|ExecStart)=' /usr/lib/systemd/system/systemd-resolved.service
ExecStart=/usr/lib/systemd/systemd-resolved
User=systemd-resolve
$ systemctl show -p User cron systemd-resolved
User=

User=systemd-resolve

systemd-resolved läuft als Systemkonto systemd-resolve (Kapitel 7, Abschnitt 1.4), cron hat keine Zeile User= und läuft als root: Es muss die geplanten Aufgaben jedes Benutzers unter dessen Namen starten können, und das darf nur root.

⁠Kurz gesagt: Mit User= läuft ein Dienst unter einem eigenen Benutzer statt als root.

HintergrundWarum Dienste unter eigenen Benutzern laufen

Ein Dienst wie systemd-resolved beantwortet Anfragen anderer Programme und verarbeitet dabei Daten von außen, etwa aus dem Netz. Steckt in ihm ein Fehler, den jemand ausnutzt, kann der Angreifer genau das tun, was der Prozess darf. Läuft der Dienst als root, ist das alles. Läuft er unter einem Systemkonto, das nur seine eigenen Dateien schreiben darf, bleibt der Schaden auf diesen kleinen Bereich begrenzt. Das ist der Grundsatz der minimalen Rechte (Cybersecurity, Kapitel 1, Abschnitt 5.2), angewandt auf Prozesse: Jedes Programm bekommt genau die Rechte, die es für seine Aufgabe braucht. Weil ein Kindprozess die Benutzernummern erbt (Unterabschnitt 1.8), gilt die Grenze auch für alles, was der Dienst selbst startet. Dass ein Konto wie systemd-resolve sich nicht anmelden kann, verhindert zusätzlich, dass jemand mit seinen Rechten eine Shell öffnet.

(b) journalctl findet keine Meldung und erklärt im Hinweis, warum: student ist in keiner der Gruppen adm und systemd-journal und darf die Meldungen des Systems nicht lesen. Gehört dein Benutzer zur Gruppe adm, siehst du dagegen fünf Meldungen und keinen Hinweis. (c) Mit sudo sind sie lesbar: systemd startet den Dienst, cron bemerkt eine leere Variable aus seiner Unit-Datei ($EXTRA_OPTS) und meldet seinen Start.

Aufgabe 23 ★★★ Neustart oder nicht

Lege die Eieruhr erneut an, diesmal ohne Abschnitt [Install] und mit Restart=on-failure. (a) Starte sie, beende ihren Hauptprozess mit kill (SIGTERM) und prüfe mit is-active. (b) Ersetze mit sed -i (Kapitel 6, Abschnitt 8.6) on-failure durch always, lies die Datei neu ein und wiederhole (a). Was ändert sich, und warum? (c) Wie hältst du einen Dienst mit Restart=always trotzdem an?

Lösung
Konsole
$ mkdir -p ~/.config/systemd/user
$ printf '[Unit]\nDescription=Eieruhr zum Üben\n\n[Service]\nExecStart=/usr/bin/sleep 600\nRestart=on-failure\n' > ~/.config/systemd/user/k8eieruhr.service
$ systemctl --user daemon-reload
$ systemctl --user start k8eieruhr
$ kill 678
$ systemctl --user is-active k8eieruhr
inactive
$ sed -i 's/on-failure/always/' ~/.config/systemd/user/k8eieruhr.service
$ systemctl --user daemon-reload
$ systemctl --user start k8eieruhr
$ systemctl --user show -p MainPID k8eieruhr
MainPID=692
$ kill 692
$ systemctl --user is-active k8eieruhr
active
$ systemctl --user show -p MainPID k8eieruhr
MainPID=696
$ systemctl --user stop k8eieruhr
$ systemctl --user is-active k8eieruhr
inactive

Statt mit einem Here-Document ist die Datei hier mit printf geschrieben; \n steht für ein Zeilenende (Kapitel 5, Abschnitt 3.1). Die PID 678 des Hauptprozesses liefert systemctl --user show -p MainPID k8eieruhr oder pgrep -f 'sleep 600'. (a) Nach SIGTERM bleibt die Eieruhr aus: Bei on-failure gilt ein Ende durch SIGTERM als gewollt. (b) Mit always startet systemd den Dienst nach jedem Ende neu; nach kill ist er wieder aktiv, mit dem neuen Hauptprozess 696. (c) Mit systemctl --user stop k8eieruhr: Nach einem stop startet systemd nie neu, denn es weiß, dass das Ende gewollt ist. Zum Aufräumen löschst du danach die Unit-Datei mit rm und liest mit systemctl --user daemon-reload neu ein.

Aufgabe 24 ★ start oder enable?

Welchen Befehl brauchst du jeweils: (a) Ein Dienst soll ab sofort laufen, aber nach dem nächsten Hochfahren nicht mehr. (b) Ein Dienst soll ab dem nächsten Hochfahren laufen, jetzt aber nicht. (c) Beides. (d) Nach systemctl enable läuft ein Dienst nicht. Ist das ein Fehler?

Lösung

(a) systemctl start dienst: läuft jetzt, enable unterbleibt. (b) systemctl enable dienst: legt nur den Link an. (c) systemctl enable --now dienst oder enable und start nacheinander. (d) Kein Fehler: enable legt nur den Link für den nächsten Start an. Ob der Dienst jetzt läuft, entscheidet allein start.

Befehlsübersicht des Moduls
Der Dienst
Definition 7.1 (Dienst, Daemon)

Ein Dienst (englisch „service“, unter Unix auch „daemon“) ist ein Programm, das im Hintergrund dauerhaft läuft und anderen Programmen oder dem System eine Leistung anbietet. Ein Dienst hat kein steuerndes Terminal, wird nicht von einer Shell gestartet und läuft oft unter einem eigenen Benutzer.

$ ps -o user:16,pid,ppid,tty,comm -C cron,chronyd,systemd-resolve,rsyslogd,dbus-daemon
↗
systemd: der Prozess mit der Nummer 1
Definition 7.2 (systemd als Dienstverwalter)

systemd ist als Prozess 1 der Dienstverwalter des Systems: Er startet beim Hochfahren die Dienste, überwacht sie, startet sie bei Bedarf neu und beendet sie beim Herunterfahren. Für jeden angemeldeten Benutzer läuft zusätzlich eine eigene Instanz systemd --user, die die Dienste dieses Benutzers verwaltet. Gesteuert wird systemd mit dem Befehl systemctl.

$ ps -o pid,ppid,user,cmd -C systemd
$ ls -l /sbin/init
$ systemctl is-system-running
↗
Die Unit
Definition 7.3 (Unit)

Eine Unit ist ein Ding, das systemd verwaltet. Ihr Name endet mit ihrer Art, etwa .service für einen Dienst, .timer für einen Zeitplan, .mount für ein eingehängtes Dateisystem oder .target für eine Gruppe von Units, die zusammen einen Zustand des Systems bilden.

$ systemctl list-units --type=service --state=running
↗
Den Zustand ansehen: systemctl status
Definition 7.4 (systemctl status, is-active, is-enabled)

systemctl status unit zeigt für eine Unit, woher ihre Beschreibung stammt und ob sie beim Start mitgestartet wird (Loaded), ihren Zustand seit wann (Active), die PID ihres Hauptprozesses (Main PID), ihren Verbrauch, ihre Prozesse (CGroup) und ihre letzten Meldungen. systemctl is-active unit und systemctl is-enabled unit antworten nur mit einem Wort.

$ systemctl status cron
↗
$ systemctl is-active cron
$ systemctl is-enabled cron
↗
Die Unit-Datei
Definition 7.5 (Unit-Datei)

Eine Unit-Datei beschreibt eine Unit in Abschnitten, deren Name in eckigen Klammern steht, und Zeilen der Form Name=Wert. [Unit] enthält allgemeine Angaben wie Description= und die Reihenfolge zu anderen Units (After=), [Service] bei einem Dienst das Programm (ExecStart=) und wie es zu betreuen ist, und [Install], wann die Unit beim Start mitgestartet wird (WantedBy=). Die Unit-Dateien des Systems liegen unter /usr/lib/systemd/system, eigene Änderungen des Verwalters unter /etc/systemd/system.

$ systemctl cat cron
↗
Ein eigener Dienst: starten und stoppen
Definition 7.6 (Benutzerdienst, start, stop)

Ein Benutzerdienst ist ein Dienst, den die Instanz systemd --user eines Benutzers verwaltet; er läuft mit den Rechten dieses Benutzers. Seine Unit-Datei liegt unter ~/.config/systemd/user, und systemctl --user richtet jeden Befehl an diese Instanz. Nach dem Anlegen oder Ändern einer Unit-Datei liest systemctl --user daemon-reload die Dateien neu ein. systemctl start unit startet eine Unit, systemctl stop unit beendet sie.

$ mkdir -p ~/.config/systemd/user
$ cat > ~/.config/systemd/user/k8eieruhr.service <<ENDE
$ systemctl --user daemon-reload
$ systemctl --user status k8eieruhr
↗
$ systemctl --user start k8eieruhr
↗
$ systemctl --user is-active k8eieruhr
↗
$ systemctl --user stop k8eieruhr
↗
systemd wacht: Neustart nach einem Absturz
Definition 7.7 (Restart=)

Die Zeile Restart= im Abschnitt [Service] legt fest, wann systemd einen beendeten Dienst neu startet: no nie (Standard), on-failure nur nach einem Fehler, always immer. Als Fehler gilt ein Exit-Status ungleich 0 und ein Ende durch ein Signal, außer durch SIGHUP, SIGINT, SIGTERM und SIGPIPE. Nach systemctl stop startet systemd nie neu. Wie lange es vor einem Neustart wartet, legt RestartSec= fest; ohne die Zeile sind es 100 Millisekunden.

$ systemctl --user show -p MainPID k8eieruhr
$ kill -9 829
$ journalctl --user -u k8eieruhr -n 4
$ kill 833
↗
Beim Start mitstarten: enable
Definition 7.8 (enable, disable)

systemctl enable unit legt fest, dass die Unit künftig mitgestartet wird, wenn das Ziel aus ihrer Zeile WantedBy= erreicht wird. Dazu legt es einen symbolischen Link im Verzeichnis <ziel>.wants an; es startet die Unit nicht. systemctl disable unit entfernt den Link wieder. Wer beides auf einmal will, schreibt enable --now.

$ systemctl --user enable k8eieruhr
$ systemctl --user is-enabled k8eieruhr
$ ls -l ~/.config/systemd/user/default.target.wants
$ systemctl --user disable k8eieruhr
↗
Dienste unter eigenen Benutzern
Definition 7.9 (User=)

Die Zeile User= im Abschnitt [Service] nennt den Benutzer, unter dem systemd das Programm des Dienstes startet. Fehlt sie, läuft ein Dienst des Systems als root. Bei einem Benutzerdienst ist die Zeile überflüssig, denn er läuft immer unter dem Benutzer seiner Instanz.

$ grep -E '^(User|ExecStart)=' /usr/lib/systemd/system/systemd-resolved.service
$ systemctl show -p User cron systemd-resolved
↗

Zusammenfassung

Begriffe
  • Dienst – Ein Dienst (englisch „service“, unter Unix auch „daemon“) ist ein Programm, das im Hintergrund dauerhaft läuft und anderen Programmen oder dem System eine Leistung anbietet.
  • Dienstverwalter – systemd ist als Prozess 1 der Dienstverwalter des Systems: Er startet beim Hochfahren die Dienste, überwacht sie, startet sie bei Bedarf neu und beendet sie beim Herunterfahren.
  • Unit – Eine Unit ist ein Ding, das systemd verwaltet.
  • Unit-Datei – Eine Unit-Datei beschreibt eine Unit in Abschnitten, deren Name in eckigen Klammern steht, und Zeilen der Form Name=Wert.
  • Benutzerdienst – Ein Benutzerdienst ist ein Dienst, den die Instanz systemd --user eines Benutzers verwaltet; er läuft mit den Rechten dieses Benutzers.
Zusammenhänge
  • Zu „Der Dienst“: Ein Dienst ist ein Programm ohne Terminal, das dauerhaft im Hintergrund für das System arbeitet, oft unter eigenem Benutzer.
  • Zu „systemd: der Prozess mit der Nummer 1“: systemd startet, überwacht und beendet als Prozess 1 die Dienste des Systems, eine eigene Instanz die jedes Benutzers; gesteuert wird es mit systemctl.
  • Zu „Die Unit“: Eine Unit ist alles, was systemd verwaltet, ein Dienst ist eine Unit mit der Endung .service; systemctl list-units zeigt sie.
  • Zu „Den Zustand ansehen: systemctl status“: systemctl status zeigt Zustand, Hauptprozess und letzte Meldungen einer Unit; is-active und is-enabled antworten mit einem Wort.
  • Zu „Die Unit-Datei“: Eine Unit-Datei beschreibt eine Unit in den Abschnitten [Unit], [Service] und [Install]; systemctl cat zeigt sie.
4 weitere zeigen
  • Zu „Ein eigener Dienst: starten und stoppen“: Ein Benutzerdienst wird mit einer Unit-Datei unter ~/.config/systemd/user angelegt und mit systemctl --user start und stop gesteuert; nach jeder Änderung der Datei folgt daemon-reload.
  • Zu „systemd wacht: Neustart nach einem Absturz“: Mit Restart=on-failure startet systemd einen Dienst neu, der mit einem Fehler oder durch ein Signal wie SIGKILL endet, nicht aber nach SIGTERM oder stop.
  • Zu „Beim Start mitstarten: enable“: enable sorgt über einen symbolischen Link dafür, dass eine Unit beim nächsten Start mitstartet, start startet sie jetzt; beides ist unabhängig voneinander.
  • Zu „Dienste unter eigenen Benutzern“: Mit User= läuft ein Dienst unter einem eigenen Benutzer statt als root.
